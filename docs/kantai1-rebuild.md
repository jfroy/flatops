# Rebuilding kantai1

kantai1 holds every Ceph OSD and both ZFS pools, so a system-disk rebuild is a planned
storage outage, not a rolling operation. This is the runbook.

Reset targets the **system disk only**. Wiping all disks takes the OSDs and the ZFS
pools with it.

```fish
talosctl -n 10.1.1.1 reset --graceful --wipe-mode system-disk --reboot
```

## What a system-disk wipe destroys

**EPHEMERAL (`/var`):**

- `/var/lib/rook` — the store of whichever mon lives on this node, plus the OSD lockbox
  keyrings, which Rook regenerates on every OSD start.
- `/var/lib/etcd` — kantai1's etcd member.
- **`/var/zfs/citerne.key` and `/var/zfs/reservoir.key`** — the native-ZFS encryption
  keys for both pools. The pools are on other disks and survive; without these files
  they stay locked and every `zfs-static` PV is unusable.
- `/var/mnt/openebs` — every `openebs-hostpath` PV pinned to kantai1. The one that
  matters is `database/pg18vc-1`; the rest are build cache, a re-downloadable GeoIP
  database, alertmanager state and the two small stash PVCs. Enumerate before starting:

  ```fish
  kubectl get pv -o json | jq -r '.items[]
    | select(.spec.storageClassName=="openebs-hostpath")
    | select(.spec.nodeAffinity.required.nodeSelectorTerms[].matchExpressions[].values[]=="kantai1")
    | "\(.metadata.name) \(.spec.claimRef.namespace)/\(.spec.claimRef.name) \(.spec.capacity.storage)"'
  ```

**STATE and META:** regenerated by `just talos apply kantai1`.

**Survives — other disks:** the three Ceph OSD NVMes (LVM metadata, LUKS headers and
bluestore data are all on-device), and the `citerne` and `reservoir` ZFS pools.

**Survives but locked:** the ZFS data is intact and unreadable until the keys are put
back. The pre-flight below is what makes that condition true.

## The Ceph situation

`storage.useAllNodes: false` and `storage.nodes` lists only kantai1, with three NVMe
devices. Every pool uses `failureDomain: osd`, because there is one host to put OSDs on.

So kantai1 holds 100% of the Ceph data: for the whole window `ceph-block` and
`ceph-bucket` are unavailable cluster-wide and every app on the default storage class is
down. Mon quorum is not a hazard — one mon per node means a wipe costs one of three and
quorum holds on kantai2 and kantai3 — but confirm that before starting.

## Where the dm-crypt keys live

Not on the ephemeral partition. The authoritative copy of each OSD's LUKS key is in the
**Ceph mon config-key store**, at `dm-crypt/osd/<osd-fsid>/luks`.

Rook's `activateOSDOnNodeCode` (the node/non-PVC OSD path that `storage.nodes` produces)
recreates the lockbox keyring from `client.admin` on every OSD start and pulls the key
from the mons. `ceph_volume/util/encryption.py` does the same `config-key get`, and
`luks_format()` feeds the secret to `cryptsetup --key-file -` over stdin. The secret is
`base64.b64encode(os.urandom(128))` — ASCII, written with **no trailing newline**.

The LUKS container is the LV, not the raw NVMe (`ROOK_CV_MODE: lvm`); both the LVM
metadata and the LUKS header live on the NVMe, which the reset does not touch. The
dependency chain:

```
k8s Secret rook-ceph-admin-keyring  (etcd)
  -> client.osd-lockbox.<osd-fsid>  (mon auth db)
    -> config-key dm-crypt/osd/<osd-fsid>/luks   (mon store.db)
      -> cryptsetup open of /dev/<vg>/osd-block-<uuid>
        -> bluestore data on the NVMe
```

One surviving mon recovers every OSD. Read the current UUIDs and device paths from the
OSD deployments:

```fish
kubectl -n rook-ceph get deploy -l app=rook-ceph-osd \
  -o jsonpath='{range .items[*]}{.metadata.labels.ceph-osd-id}{"\t"}{.spec.template.spec.containers[?(@.name=="osd")].env[?(@.name=="ROOK_OSD_UUID")].value}{"\t"}{.spec.template.spec.containers[?(@.name=="osd")].env[?(@.name=="ROOK_BLOCK_PATH")].value}{"\n"}{end}'
```

## Pre-flight

Snippets are fish.

### Verify the ZFS encryption keys — hard gate

**The one irreversible step.** Both pools use native encryption and the keys live on the
partition being wiped. Unlike the dm-crypt keys there is **no second copy anywhere in
the cluster**; 1Password is the only other copy. If it is wrong or incomplete, the wipe
turns roughly 246 TiB into ciphertext with no recovery path.

The check is not "the keys are in 1Password" — it is "the 1Password copies are
byte-identical to what is on the node."

What unlocks the pools at boot is the Talos zfs extension service
(`siderolabs/extensions`, `storage/zfs/zfs-service/main.go`), which runs exactly
`zpool import -fal`. The `-l` resolves each encryption root's `keylocation`, which points
at `file:///var/zfs/<pool>.key`. After a wipe the import still succeeds but the datasets
come up `keystatus=unavailable` and unmounted.

Talos has no shell, so this goes through a privileged debug pod:

```fish
kubectl -n kube-system debug -it --profile sysadmin --image=alpine node/kantai1 \
  -- chroot /host sh -c '
    sha256sum /var/zfs/citerne.key /var/zfs/reservoir.key
    ls -l /var/zfs/
    zfs get -H keyformat,keylocation,keystatus citerne reservoir
  '
```

Keep all three outputs. The hashes are what you compare 1Password against — do it now,
not after the wipe. `ls -l` gives the mode and ownership to restore. If `keyformat` is
`raw` the key is 32 raw bytes and must round-trip byte-exact: a trailing newline, a
charset conversion, or 1Password storing it as a text field instead of a file attachment
corrupts it silently.

**Do not proceed until both hashes match what 1Password gives back.**

### Dump the dm-crypt keys

Defence-in-depth, since the mon store survives on the other two nodes. It costs one
command and it is the only thing that survives losing the mon store to something other
than this rebuild.

```fish
function ceph-tool
    kubectl -n rook-ceph exec deploy/rook-ceph-tools -- $argv
end

for fsid in (kubectl -n rook-ceph get deploy -l app=rook-ceph-osd \
    -o jsonpath='{range .items[*]}{.spec.template.spec.containers[?(@.name=="osd")].env[?(@.name=="ROOK_OSD_UUID")].value}{"\n"}{end}')
    printf '%s %s\n' $fsid (ceph-tool ceph config-key get "dm-crypt/osd/$fsid/luks")
end
```

Read them off the screen and put them straight into OpenBao rather than redirecting to a
file. Then prove each one opens its device, from inside the OSD pod — `--test-passphrase`
creates no mapping:

```fish
set pod (kubectl -n rook-ceph get pod -l app=rook-ceph-osd,ceph-osd-id=0 -o name)
set key '<the key for that OSD>'
set lv  '<its ROOK_BLOCK_PATH>'

printf %s $key | kubectl -n rook-ceph exec -i $pod -c osd -- \
    cryptsetup luksOpen --test-passphrase --key-file - $lv
and echo KEY-OK
```

`printf %s`, not `echo` — a trailing newline is not part of the passphrase. Repeat for
the other two.

Store the dump off the cluster. A key backup that only exists inside the cluster you are
about to take down is not a backup.

### Confirm the mons are still spread

```fish
kubectl -n rook-ceph get pod -l app=rook-ceph-mon -o wide
kubectl -n rook-ceph get cm rook-ceph-mon-endpoints -o jsonpath='{.data.mapping}'
ceph-tool ceph mon dump
```

Three mons, one per node, all in quorum, `outOfQuorum` empty. A mon that cannot schedule
never joins the monmap, so a Pending mon leaves a two-mon monmap whose quorum is 2 — and
then losing kantai1 *would* drop quorum.

**If they have drifted back onto one node**, config alone will not fix it. Mon node
assignment is sticky: Rook records it in that `mapping` key because the store is a
hostPath, gives the mon a hard `nodeSelector`, and strips its anti-affinity. Only a
failover relocates a mon, and the automatic trigger sits behind a package-level var set
at operator start and cleared on the first healthy pass. So **restart
`rook-ceph-operator`**, once per mon you need moved, waiting for three mons in quorum in
between. Mechanism in [kantai-placement.md](kantai-placement.md) §2.

The mgrs need nothing — no hostPath store, and their required `podAntiAffinity` plus
kantai2's `node.kantai.xyz/low-memory:NoSchedule` taint already pin one to kantai1 and
one to kantai3.

### Confirm the Postgres replica is live off kantai1

```fish
kubectl -n database get cluster pg18vc \
  -o jsonpath='{.status.currentPrimary}{"\n"}{.status.instancesStatus}{"\n"}'
kubectl -n database get pod -l cnpg.io/cluster=pg18vc -o wide
```

What you need: `pg18vc-1` primary on kantai1, `pg18vc-2` healthy **on kantai3**, both on
the same `timeLineID`, `ContinuousArchiving: True`. That makes the rebuild a failover
rather than a restore. If both pods are on kantai1, the anti-affinity was merged but
never acted on — bound PVCs are node-affine and beat any affinity rule, so it is a
one-shot decision taken when a PVC is created. Re-run `kubectl cnpg destroy pg18vc 2`
and wait for the `pg_basebackup` re-clone. Reasoning in
[kantai-placement.md](kantai-placement.md) §3.

**Still take a fresh offsite copy.** A replica protects against losing the node, not
against losing the data logically, and WAL archiving stops for the duration by design.
Trigger a CNPG backup, let the WAL archive catch up, run the `pg18vc-backup` CronJob
manually, then verify the R2 side independently — list `kantai-pg18vc` and check the
newest base backup is the one you just took. Confirm the latest kopiur snapshots are
green too.

## Boot media

After the reset kantai1 has no bootloader and needs an external image to reach
maintenance mode. Assets come from the self-hosted factory at `tif.etincelle.cloud`, at
`/image/<schematic-id>/<version>/<artifact>`:

| artifact | use |
| --- | --- |
| `metal-amd64-secureboot.iso` | BMC virtual media |
| `metal-amd64-secureboot-uki.efi` | UEFI HTTP boot — one signed EFI binary |
| `metal-amd64-secureboot` (under `/pxe/…`) | iPXE script, if netboot is ever wired up |

A leading `v` on the version is optional. Use the version pinned in `talos/topf.yaml`.

**kantai1's schematic ID is `aee0d5fc4efec81c84607d4bd2074670e675260f3421a413e52b6e808e33ee2b`.**
Schematic IDs are version-independent — a hash of the schematic document — so this holds
across Talos versions as long as `talos/schematics/kantai1.yaml` is unchanged.

**Do not use `just talos schematic-ids` to identify a node's ID.** topf ignores
`--nodes-filter` and prints bare, deduplicated, sorted IDs with no hostnames:
`internal/cmd/schematicids` iterates `t.Config().Nodes` rather than
`t.FilteredNodes(ctx)`. The Just recipe therefore does not accept a hostname.
For a labelled answer, render the config — `machine.install.image` is built
from `factory` + the node's `schematicId` + `talosVersion` + `secureboot`:

```fish
just talos render kantai1
grep -m1 'image:' talos/output/kantai1.yaml
rm -rf talos/output   # it holds cluster secrets in plaintext
```

**Pre-warm the URL before pointing firmware at it.** The factory builds assets on demand
and caches them, and kantai1's is the fat one — nvidia, zfs, kata. A cold build has
previously taken long enough to time out an installer pre-pull four times; firmware HTTP
boot has a much shorter fuse.

```fish
curl -fL -o /dev/null -w '%{http_code} %{size_download} %{time_total}\n' \
  "https://tif.etincelle.cloud/image/<schematic-id>/<version>/metal-amd64-secureboot-uki.efi"
```

### The hardware

kantai1 is **not** a Dell. AMI Aptio Setup Utility on an AMD platform, three Micron 9300
NVMe SSDs (the Ceph OSDs), Mellanox NICs, behind a MegaRAC-style BMC at `kantai1-ipmi`.
The `observability/idrac-exporter` app is `mrlhansen/idrac_exporter`, a **generic
Redfish** exporter — its OpenBao key is named `kantai1-redfish`. No iDRAC, but Redfish is
there with credentials already in OpenBao.

### UEFI HTTP boot

The UKI is one signed EFI application containing kernel, initramfs and the schematic's
`extraKernelArgs`. No TFTP, no iPXE chain. In BIOS setup the entry is *Advanced →
`MAC:<mac>-HTTP Boot Configuration`*, one per NIC. It does **not** appear in the BMC's
web BIOS-settings page, and probably not in Redfish `Bios.Attributes` either — that form
is published by the Mellanox UEFI driver through HII at POST, not part of the static AMI
setup attribute map.

What decides whether it works:

- **HTTPS trust.** The firmware validates the TLS certificate itself. If
  `tif.etincelle.cloud` presents an internal CA, upload that CA to the BIOS HTTP-boot
  trust store, or serve the UKI over plain HTTP on the LAN for the duration.
- **SecureBoot signature.** The firmware verifies the UKI against `db`. SecureBoot keys
  live in motherboard NVRAM, not on disk, so a reset does not disturb enrollment. A
  failure here is a clean refusal to boot, not a dangerous state.
- **Do not "fix" a boot failure by disabling SecureBoot.** kantai1's `EPHEMERAL` and
  `STATE` use TPM-sealed LUKS with `checkSecurebootStatusOnEnroll: true`
  (`talos/node/kantai1/40-volumes.yaml`). Installing with SecureBoot off would fail
  enrollment or bind the volumes in a state you do not want. Fall back to virtual media
  instead.
- **It is one-shot by design.** Once `just talos apply` installs to disk, the installer
  writes sd-boot and the UKI to the fresh ESP and creates its own EFI boot entry. Check
  the boot order afterwards so the HTTP entry has not stayed ahead of the disk.

### Driving it over Redfish

Avoids typing the URL at a KVM viewer with no paste. Credentials are in OpenBao under
`kantai1-redfish`. Discover first — do not assume paths or supported fields:

```fish
curl -sk -u $U:$P https://$BMC/redfish/v1/Systems | jq .
curl -sk -u $U:$P https://$BMC/redfish/v1/Systems/1 | jq '.Boot, .Actions'
curl -sk -u $U:$P https://$BMC/redfish/v1/Managers/1/VirtualMedia | jq .
```

Look for `HttpBootUri` plus `UefiHttp` in `BootSourceOverrideTarget@Redfish.AllowableValues`
— the DMTF-standard path, which goes through the BMC boot manager rather than the NIC HII
form, so it can work even though the form is invisible to the web UI:

```fish
curl -sk -u $U:$P -X PATCH https://$BMC/redfish/v1/Systems/1 \
  -H 'Content-Type: application/json' -H 'If-Match: *' \
  -d '{"Boot":{"HttpBootUri":"<uki url>","BootSourceOverrideTarget":"UefiHttp","BootSourceOverrideEnabled":"Once"}}'
```

Or **VirtualMedia with `InsertMedia`**, the higher-probability path on MegaRAC. Unlike
the KVM viewer's "Browse File", `InsertMedia` hands the BMC a URL and it fetches the ISO
itself:

```fish
curl -sk -u $U:$P -X POST \
  "https://$BMC/redfish/v1/Managers/1/VirtualMedia/CD1/Actions/VirtualMedia.InsertMedia" \
  -H 'Content-Type: application/json' \
  -d '{"Image":"<iso url>","Inserted":true,"WriteProtected":true}'

curl -sk -u $U:$P -X PATCH https://$BMC/redfish/v1/Systems/1 \
  -H 'Content-Type: application/json' -H 'If-Match: *' \
  -d '{"Boot":{"BootSourceOverrideTarget":"Cd","BootSourceOverrideEnabled":"Once"}}'

curl -sk -u $U:$P -X POST \
  "https://$BMC/redfish/v1/Systems/1/Actions/ComputerSystem.Reset" \
  -H 'Content-Type: application/json' -d '{"ResetType":"ForceRestart"}'
```

Notes that bite: the system path is `/redfish/v1/Systems/1` on AMI/MegaRAC, not Dell's
`System.Embedded.1` — take it from the `Systems` collection. MegaRAC often requires
`If-Match` on PATCH. And pre-warm the factory URL first: the BMC's own download times out
on a cold build exactly like firmware would.

If none of that works, shorten the URL rather than fighting the console — a redirect like
`http://boot.kantai.xyz/k1` → the factory asset makes manual entry trivial, is reusable
for the other two nodes, and sidesteps the firmware TLS-trust question. Failing that, the
KVM viewer's own virtual media still works with a locally-downloaded ISO.

## Procedure

1. Pre-flight in full. The ZFS key hash check is a hard gate — if the 1Password copies do
   not match the node, stop, because nothing later recovers from that.
2. Take a fresh etcd snapshot and **copy it off the cluster**. The `talos-backup` PVC is
   on `ceph-block`, so a snapshot taken during the outage has nowhere to go.
3. Cordon kantai1 and quiesce everything using `ceph-block` / `ceph-bucket` rather than
   letting it error. `pg18vc` is the exception — leave it running; losing kantai1 fails
   the primary over to `pg18vc-2` on kantai3 and every app on `pg18vc-rw` follows the
   service. Expect slower queries, and expect `ContinuousArchiving` to go False while the
   RGW is down. Watch free space on the promoted primary's PV: unarchived WAL accumulates
   in `pg_wal` until the RGW is back.
4. `ceph osd set noout` — with all OSDs on one host there is nowhere to rebalance to, and
   you want the same OSDs back.
5. Let the OSD pods stop cleanly:
   `kubectl -n rook-ceph scale deploy -l app=rook-ceph-osd --replicas=0`.
6. **Scale the Rook operator to 0** for the duration. Optional but tidy: the mon on
   kantai1 goes out of quorum, the operator tries to fail it over after
   `ROOK_MON_OUT_OF_QUORUM_TIMEOUT`, finds no free node — one mon per node, kantai1 is
   the only free slot — and reverts. Harmless churn that fills the log.
7. Remove kantai1's etcd member: `talosctl -n 10.1.1.1 reset --graceful` does the etcd
   leave. Two of three remain and quorum holds, but there is no further failure tolerance
   until kantai1 is back, so do not start this while kantai2 is unhealthy.
8. Reset the system disk only (command at the top of this document).
9. Boot the secureboot image into maintenance mode — UEFI HTTP boot from the factory UKI,
   or BMC virtual media with the ISO, driven over Redfish so there is no URL to type. Do
   not skip the pre-warm.
10. `just talos apply kantai1`.
11. Node rejoins, TPM re-enrolls EPHEMERAL and STATE, the etcd member re-adds. Scale the
    Rook operator back to 1 once kantai1 is `Ready`.
12. **Restore the ZFS keys** before anything expects the pools.
13. Bring the rest of the storage back.

## Bringing the storage back

### ZFS: restore the keys first

Nothing touching the pools works until this is done, and `storage/kantai1-samba`, immich
(`reservoir/photos`), the media PVs, `storage/storage-pv` and stash's `/mnt/citerne/media`
sit in a mount-failure loop meanwhile. Do it as soon as kantai1 is `Ready`.

`zpool import -fal` at boot will have imported both pools and failed to load their keys,
so the datasets are present but `keystatus=unavailable` and unmounted.

```fish
# repeat for reservoir.key. Piping through base64 keeps the bytes intact and keeps the
# key off the command line; substitute however you get it out of 1Password.
op read "op://<vault>/kantai1-zfs/citerne.key" | base64 | tr -d '\n' | \
  kubectl -n kube-system debug -i --profile sysadmin --image=alpine node/kantai1 \
    -- chroot /host sh -c 'mkdir -p /var/zfs && base64 -d > /var/zfs/citerne.key && chmod 0400 /var/zfs/citerne.key'
```

Verify against the hashes captured pre-flight — this is the check that catches a mangled
round-trip — then unlock:

```fish
kubectl -n kube-system debug -it --profile sysadmin --image=alpine node/kantai1 \
  -- chroot /host sh -c '
    sha256sum /var/zfs/citerne.key /var/zfs/reservoir.key
    zfs load-key -a
    zfs mount -a
    zfs get -H keystatus citerne reservoir
  '
```

Both encryption roots must report `keystatus available`. A reboot works too, but
`load-key` + `mount` avoids one. Restore the mode and ownership recorded pre-flight — ZFS
reads a key file with looser permissions, so a wrong mode fails quietly as a security
problem rather than loudly as a broken one.

Once mounted, the `zfs-static` PVs bind normally: the driver bind-mounts each dataset's
own `mountpoint` under `/host`.

### Ceph: the OSDs re-activate themselves

With `/var/lib/rook` gone, Rook treats kantai1 as a fresh node. The `osd-prepare` job runs
`ceph-volume lvm list` against the three devices, finds the existing OSDs from the
on-device LVM tags, and the operator creates OSD deployments running
`activateOSDOnNodeCode`, which recreates the lockbox keyring from `client.admin` and pulls
the LUKS key from the mons. The OSDs keep IDs 0, 1 and 2.

**Expect the kantai1 mon to be replaced, not repaired.** Its store was on the wiped
partition and its deployment carries a hard `kubernetes.io/hostname: kantai1`
nodeSelector. Rook fails it over to a fresh mon id, which schedules back onto kantai1 —
the only node without a mon once the old one is scaled down — and syncs its store from
the other two. A new mon letter is normal; a replacement stuck Pending is not, and means
the anti-affinity has nowhere to put it.

Watch for, in order:

1. `rook-ceph-osd-prepare-kantai1` logs listing three **existing** OSDs — not proposing
   to create new ones. If it proposes new OSDs, stop immediately and do not let it run;
   that is the one failure mode that destroys data.
2. `ceph -s` back in quorum with all three OSDs `up`/`in`, and three mons again, one per
   node. Re-check the `rook-ceph-mon-endpoints` `mapping`.
3. `ceph osd unset noout`, then let recovery settle to `HEALTH_OK`.
4. The tuppr `CephCluster` health check gates on `HEALTH_OK` exactly, and the three
   `AUTH_INSECURE_*` warnings are muted rather than fixed — if muting ever lapses,
   upgrades block.

### If the OSDs do not come back

In order of escalation:

1. **Mons lost quorum but one store survives** — Rook's disaster-recovery guide covers
   restoring quorum from a single mon (`ceph-mon --extract-monmap`, edit, inject). The
   config-key store, and the keys, come back with it.
2. **All mon stores lost** — rebuild the mon store from the OSDs with
   `ceph-monstore-tool ... rebuild`, then re-inject the dm-crypt keys from the pre-flight
   dump with `ceph config-key set dm-crypt/osd/<fsid>/luks <key>`.
3. **Manual open** — with those keys you can always
   `cryptsetup luksOpen --key-file - /dev/<vg>/osd-block-<uuid> <name>` by hand and read
   bluestore directly. This is why the dump is not optional.

### Postgres: re-clone, do not restore

`pg18vc-2` on kantai3 carried the database through the outage and is now primary.
`pg18vc-1`'s PVC pointed at a directory on the wiped partition, so its pod will not start.
That is expected and is not a reason to reach for `recovery-job.yaml`:

```fish
kubectl cnpg destroy pg18vc 1
```

The anti-affinity puts it back on kantai1, it re-clones via `pg_basebackup`, and once
healthy you can hand the primary back with `kubectl cnpg promote pg18vc pg18vc-1`. Then
check `ContinuousArchiving` returns to True once the RGW is serving, and confirm the next
`pg18vc-backup` run lands in R2 — the WAL gap means the offsite copy is stale until then.

The small stash PVCs come back from their kopiur snapshots; the buildkit,
netronome-geoip and alertmanager PVs just refill.

## Accepted design, not open work

Recorded so it is not re-opened as a finding.

**Critical state is spread.** One mon per node, one mgr each on kantai1 and kantai3, and a
live Postgres replica on kantai3. That is what makes this rebuild two failovers rather
than a restore.

**kantai1 carries no `node-role.kubernetes.io/control-plane:PreferNoSchedule` taint**
while kantai2 and kantai3 do. Deliberate, and it stays: everything without explicit
placement lands on the big node, which is where it belongs. The answer for state that must
not be there is explicit placement, not a scheduler nudge.

**`dataDirHostPath` stays on EPHEMERAL.** `/var/lib/rook` is the chart default and is not
moving to a `UserVolumeConfig` on a non-system disk. A system-disk wipe takes the mon
store of whichever mon lives there; with one mon per node that costs one of three and Rook
rebuilds it by failover. The cost is bounded precisely because the mons are spread — if
mon placement ever changes, re-read this before assuming a node rebuild is still cheap.

**WAL archiving pauses during the rebuild.** `ObjectStore pg18vc-local-ceph` points at
`https://s3.kantai.xyz`, the RGW on kantai1's own OSDs, and is not being repointed.
`ContinuousArchiving` goes False shortly after the OSDs stop and `LastBackupSucceeded`
goes stale; both are expected. Postgres retains WAL in `pg_wal` on the promoted primary
while `archive_command` fails, so free space on that PV is the number worth watching. A
short window is fine; an unplanned multi-day outage is where this bites. Nothing needs
doing to recover — archiving resumes and drains when the RGW is back.

**The ZFS keys live only on EPHEMERAL.** Putting them somewhere that survives a wipe (a
`UserVolumeConfig` on a non-system disk, or a file from a SOPS-encrypted secret) would
remove the manual step, and is deliberately not being done. The mitigation is procedural
and it is the strictest gate here: hash-verify against the node before the wipe, restore
and re-verify after. There is no recovery from getting this wrong.

**The etcd snapshot lands on Ceph.** `talos-admin/talos-backup` writes `/data/etcd.boltdb`
to a `ceph-block` PVC and reaches R2 only through kopiur's snapshot of that PVC, so no new
snapshot can be taken or shipped while Ceph is down. Same class of coupling as the WAL
archive, accepted on the same grounds. The mitigation is step 2 of the procedure, and it
is load-bearing — do not skip it because talos-backup runs nightly.
